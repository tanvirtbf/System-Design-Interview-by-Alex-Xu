# Database এবং Which Databases to Use? (Chapter 1)

# Part 1: Database (Web tier আর Data tier আলাদা করা)

## সমস্যা কী ছিল?

Single server setup এ web app, database সব এক machine এ ছিল। User বাড়লে একটা server আর যথেষ্ট থাকে না। তখন **একাধিক server** লাগে:

- একটা server **web/mobile traffic** এর জন্য (এটাকে বলে **web tier**)
- আরেকটা server **database** এর জন্য (এটাকে বলে **data tier**)

### Figure 1-3 (নিজের আঁকা)

```
                    WEB TIER                      DATA TIER
                +---------------+             +---------------+
  Users ------> |  Web Server   | ----------> |   Database    |
 (Web/Mobile)   | (Express app) |             |  (MySQL etc.) |
                +---------------+             +---------------+
```

## কেন আলাদা করা হয়?

বইয়ের মূল কথা: web tier আর data tier আলাদা করলে **দুটোকে আলাদাভাবে scale** করা যায়।

উদাহরণ:
- Traffic বাড়লে শুধু web server বাড়ালেন, database যেমন ছিল তেমন।
- Data অনেক বেড়ে গেলে শুধু database বড় করলেন, web server ছোঁয়া লাগলো না।

একসাথে থাকলে একটা বাড়াতে গেলে পুরো machine বদলাতে হতো।

### বাড়তি ব্যাখ্যা (বইয়ের বাইরে)

- আলাদা হওয়ার আরেকটা সুবিধা হলো resource এর লড়াই বন্ধ হওয়া। আগে web app আর database একই CPU ও RAM ভাগ করে চালাত, এখন প্রত্যেকের নিজের resource।
- Security ও ভালো হয়: database কে public internet থেকে আড়ালে রেখে শুধু web server কে তার সাথে কথা বলতে দেওয়া যায়।

# Part 2: Which Databases to Use?

Data tier এ কোন ধরনের database নেবেন, সেটা বড় সিদ্ধান্ত। বইয়ে দুই ধরনের কথা বলা হয়েছে।

## 1. Relational Database (SQL)

- আরেক নাম: **RDBMS** (Relational Database Management System) বা **SQL database**।
- জনপ্রিয় উদাহরণ: **MySQL, Oracle Database, PostgreSQL**।
- Data রাখা হয় **table এর মধ্যে row ও column আকারে**।
- সবচেয়ে বড় সুবিধা: SQL দিয়ে **join operation** করা যায়, মানে আলাদা আলাদা table এর data একসাথে জোড়া দিয়ে বের করা যায়।

### উদাহরণ (বাড়তি ব্যাখ্যা)

মুদি দোকানের POS এ দুটো table ধরেন:

```
products                         sales
+----+---------+-------+        +----+------------+----------+
| id | name    | price |        | id | product_id | quantity |
+----+---------+-------+        +----+------------+----------+
| 1  | Rice    | 70    |        | 1  | 1          | 5        |
| 2  | Oil     | 180   |        | 2  | 2          | 2        |
+----+---------+-------+        +----+------------+----------+
```

`sales.product_id` দিয়ে `products` table এর সাথে join করে জানা যায়, "কোন পণ্য কতটা বিক্রি হলো ও দাম কত?"

## 2. Non-Relational Database (NoSQL)

- আরেক নাম: **NoSQL database**।
- জনপ্রিয় উদাহরণ (বইয়ের তালিকা): **CouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB**।
- বইয়ের মতে সাধারণত এগুলোতে **join operation সমর্থিত নয়**।

### NoSQL এর চার ধরন (বইয়ের বিভাগ)

| ধরন | সংক্ষেপে কী | বাড়তি উদাহরণ |
|---|---|---|
| **Key-value store** | একটা key দিয়ে একটা value রাখা ও আনা | Redis, DynamoDB |
| **Graph store** | সম্পর্ক (node ও edge) নিয়ে কাজ | Neo4j |
| **Column store** | column অনুযায়ী data সাজানো | Cassandra, HBase |
| **Document store** | JSON-এর মতো document হিসেবে data রাখা | CouchDB, MongoDB |

(বইয়ে শুধু চার ধরনের নাম আছে, প্রতিটার সাথে উদাহরণ আমি যোগ করেছি।)

---

## কোনটা বেছে নেবেন?

### বইয়ের সিদ্ধান্ত

অধিকাংশ developer এর জন্য **relational database ই সেরা বিকল্প**। কারণ:
- এটা **৪০ বছরের বেশি** সময় ধরে আছে।
- ইতিহাসে এটা ভালোভাবেই কাজ করেছে।

কিন্তু relational database যদি আপনার নির্দিষ্ট use case এ না মানায়, তখন তার বাইরে খুঁজে দেখা **জরুরি**।

### NoSQL বেছে নেওয়া উচিত যখন (বইয়ের ৪টা শর্ত)

1. আপনার application এ **অতি-কম latency** দরকার।
2. আপনার data **unstructured**, অথবা আপনার কোনো relational data নেই।
3. আপনাকে শুধু data **serialize ও deserialize** করতে হয় (JSON, XML, YAML ইত্যাদি)।
4. আপনাকে **বিপুল পরিমাণ data** রাখতে হবে।

### সংক্ষেপে তুলনা

```
                  SQL (Relational)            NoSQL (Non-relational)
Data রাখে         Table, row, column          Key-value / Graph /
                                              Column / Document
Join              SQL দিয়ে করা যায়           সাধারণত support করে না
বইয়ের পরামর্শ    বেশিরভাগ ক্ষেত্রে ডিফল্ট    ৪টা শর্তের কোনোটা মিললে
উদাহরণ            MySQL, PostgreSQL, Oracle   Cassandra, DynamoDB, Neo4j
```

## আপনার POS এর জন্য প্রয়োগ (বাড়তি ব্যাখ্যা)

আপনি আগে মুদি দোকানের POS এর কথা বলেছিলেন (Express + React Native)। এখানে data হলো পণ্য, বিক্রি, customer, বাকির হিসাব। এগুলো পরস্পর সম্পর্কিত (বিক্রি → পণ্য, বিক্রি → customer), আর টাকার হিসাব নির্ভুল থাকতে হবে।

তাই বইয়ের নিয়ম অনুযায়ীও **relational database (PostgreSQL বা MySQL)** এখানে স্বাভাবিক পছন্দ। NoSQL এর ৪টা শর্তের কোনোটাই এই সাধারণ POS এ জোরালোভাবে খাটে না।

## Interview তে কীভাবে বলবেন?

বইয়ের কথা ধরে একটা ভালো উত্তর হবে এমন:

> "আমি শুরুতে relational database নেব, কারণ এটা mature, আর আমার data এ relation আছে। যদি requirement এ অতি-কম latency বা বিপুল unstructured data আসে, তখন NoSQL বিবেচনা করব।"

এখানে মূল জিনিস হলো **সিদ্ধান্তের পেছনে যুক্তি দেখানো**। কোনো একটা বেছে নিয়ে "এটাই সেরা" বলা নয়।

## মনে রাখার পয়েন্ট

| বিষয় | সারকথা |
|---|---|
| Web tier ও Data tier | আলাদা server এ রাখলে আলাদাভাবে scale করা যায় |
| Relational DB | Table ও row, join করা যায়, ৪০+ বছরের পরীক্ষিত |
| Non-relational DB | চার ধরন, সাধারণত join নেই |
| ডিফল্ট পছন্দ | বেশিরভাগ ক্ষেত্রে relational |
| NoSQL কখন | অতি-কম latency / unstructured data / শুধু serialize-deserialize / বিপুল data |
